# Project Overview

**AI-Powered Test Automation & Intelligence** (product name — internal package/class names
throughout the codebase, e.g. `com.testplatform`, `test-orchestrator`, remain unchanged; see
Architectural Decisions) is a self-hosted platform for running, watching, and reviewing a
Playwright + Cucumber BDD test suite. It wraps a pre-existing standalone test framework
(`engine/`) with a web UI (`frontend/`) and an orchestrator API (`backend/`), persists
every run's results to Postgres, and exposes historical analytics through Grafana.

Four independently-deployable pieces, one docker-compose:

```
engine/      Playwright + Cucumber + TypeScript BDD framework (pre-existing, lightly patched)
backend/     Spring Boot orchestrator — triggers runs, streams console output, parses
             cucumber.json, persists to Postgres
frontend/    React + Vite + Tailwind console UI
grafana/     Provisioned datasource + starter dashboard reading Postgres directly
```

The `engine/` folder is explicitly called out in `README.md` as "the Playwright + Cucumber
BDD test framework you already had" — i.e. it predates and is logically independent of the
backend/frontend. Treat it as the thing being orchestrated, not as application code that
was designed alongside the orchestrator.

# Core Architecture

Corrected, verified end-to-end flow (confirmed against source, not just the README):

```
User (browser)
  → Frontend (React) — POST /api/runs with RunRequest (environment name, tags, browser,
    headless, parallelWorkers, screenshot/video/traceMode — no raw URLs)
  → Backend RunController.trigger() → TestRunnerService.enqueue()
      - EnvironmentConfigService.resolve(environment) → {baseUrl, apiBaseUrl}, or a 400
        if the name is unknown/unconfigured (see Architectural Decisions) — resolved
        BEFORE any DB row is created
      - saves TestRun row (including environment + the resolved URLs), status=QUEUED
      - submits to a single-threaded ExecutorService ("cucumber-run-queue")
  → TestRunnerService.executeRun()
      - status=RUNNING
      - spawns a child process: `npm test -- --tags <expr>` with cwd=engine/
      - maps RunRequest fields + the resolved environment onto env vars the engine
        already understands: HEADLESS, BROWSER, SCREENSHOT, VIDEO, TRACE,
        PARALLEL_WORKERS, BASE_URL, API_BASE_URL (from the resolved environment, not the
        request), plus REPORT_DIR=reports/run-<id>
      - reads the child's stdout line-by-line, forwards each line to LogBroadcastService
  → Engine process (Node/tsx, engine/cucumber.cjs)
      - config/framework.yaml resolves ${ENV_VAR} placeholders (config.ts)
      - Cucumber runs features/**/*.feature using step defs in src/steps/*.steps.ts
      - hooks.ts: one Playwright browser per worker (BeforeAll), one isolated
        BrowserContext+Page per scenario (Before/After)
      - steps resolve locators via config/locators/*.yaml (locator-registry.ts)
      - on scenario end: screenshot/video/trace captured per config, attached to the
        Cucumber report via `this.attach(...)`; every DSL step also attaches a
        text/plain start/pass-fail log line (logger.ts runLoggedStep)
      - writes reports/run-<id>/cucumber.json + cucumber.html
  → Backend LogBroadcastService fans out each stdout line over SSE
      (GET /api/runs/{id}/stream) → Frontend LogConsole (Jenkins-style live console),
      and buffers everything so late subscribers replay the backlog
  → On process exit: TestRunnerService.finalizeRun()
      - CucumberJsonParserService parses reports/run-<id>/cucumber.json into
        FeatureResult → ScenarioResult → StepResult → Attachment JPA entities
      - each embedding's base64 bytes are decoded and re-encrypted (AES-256-GCM,
        AttachmentCipher) before being attached to the entity graph
      - TestRun status is set to PASSED / FAILED / ERRORED based on parsed counts
        (or a timeout/launch failure)
      - the whole tree is persisted to Postgres in one transaction
  → Frontend Dashboard / History / RunDetail / StepsExplorer pages query the backend's
    REST API (JPA Specifications for filtering); screenshots are fetched decrypted via
    GET /api/attachments/{id}
  → Grafana (separate container) reads the SAME Postgres directly via read-only SQL
    views (v_scenario_detail, v_step_detail, v_run_daily_stats, v_tag_failure_stats,
    v_step_failure_stats) — it has no decryption key, so it can only ever show decoded
    metadata (status/duration/tags/error text), never screenshot bytes.
```

**Concurrency model:** only one engine process runs at a time — the run queue is a
single-threaded `ExecutorService`. This exists because all runs share the same `engine/`
checkout (`node_modules`, and previously a shared report path); two concurrent processes
would race on that. Parallelism happens *within* a run via Cucumber's own `--parallel`,
driven by `PARALLEL_WORKERS`, where each worker owns an isolated browser/context/auth
state. **Do not casually "fix" this by running the queue concurrently** — see
Architectural Decisions.

# Frontend

- React 18 + TypeScript + Vite + Tailwind CSS, React Router v6 for routing, Recharts for
  charts, date-fns for formatting.
- Product name shown in the UI (browser tab title, sidebar brand lockup) is
  **"TestGenie"** with **"AI-Powered Test Automation & Intelligence"** as the tagline
  underneath — a display/branding rename only. Internal identifiers
  (`com.testplatform` package, `test-orchestrator`/`test-orchestrator-ui` artifact
  names, Docker container names, DB name `test_platform`) were deliberately **not**
  renamed — see Architectural Decisions for why, and don't casually "finish the rename"
  into those without discussing it first.
- Single-page app, six routes wired in `App.tsx`: `/` (Mission Control / Dashboard),
  `/run` (RunTest — trigger form + live console, both execution modes), `/history`
  (paginated run list), `/runs/:id` (RunDetail — scenario grid + console tab),
  `/explorer` (StepsExplorer — the flattened cross-run step grid), `/visual-debug/:id`
  (VisualDebugView — dedicated live view for a Visual Debug run).
- `pages/RunTest.tsx` starts with an **Execution Mode** segmented control (Standard
  Execution / Visual Debug) above everything else, then branches into two largely
  independent panels with **separate React state** (`form` vs `vdEnvironment`/
  `vdScenario`) — switching modes never leaks one mode's selection into the other.
  - **Standard**: the pre-existing numbered 3-step workflow — **1. Environment**
    (`EnvironmentPicker`) → **2. Test suite** (`TagPicker`) → **3. Execution options**
    (browser/workers/headless/artifact modes) — followed by Run. Unchanged by Visual
    Debug's addition.
  - **Visual Debug**: **1. Environment** → **2. Scenario** (`ScenarioPicker` — a
    single-select radio group, not a multi-select, so "only one scenario" is true by
    construction, not just validated after the fact) → **3. Start Visual Debug**
    (browser/headless/workers are shown as fixed, forced text, not controls). Submits to
    `POST /api/visual-debug`, then navigates to `/visual-debug/{id}` — this page's own
    live console/stats never render for this mode, the dedicated view owns that.
  - Once a Standard run is triggered, `RunTest` polls `GET /api/runs/{id}` every 4s
    (same pattern as `RunDetail.tsx`) to show live pass/fail/skipped/duration via
    `MiniStat` alongside `LogConsole`. It also captures `detail.consoleLog` on every
    poll tick (not just `.summary`) and passes it to `LogConsole` as `staticLog` —
    **without this, the console visibly wipes back to "Waiting for output…" the
    instant a run finishes**, since `LogConsole`'s own `!live` branch falls back to
    `staticLog` and RunTest used to never provide one. Real bug, caught by actually
    driving the running app in a browser, not just building/typechecking — see
    Validation and Testing. `VisualDebugView.tsx` has the exact same fix for the same
    reason, applied independently since it polls separately.
- `pages/VisualDebugView.tsx` seeds its execution-steps checklist from the scenario's
  pre-fetched step list (`GET /api/scenarios`, matched by uri+line) and advances it by
  step **order**, not by matching step text against log messages — Cucumber always runs
  a single scenario's steps in declared order, so sequence is reliable and avoids fuzzy
  text-matching against Gherkin wording that isn't guaranteed identical to the logged
  description. Two independent code paths update it, both necessary: a live SSE
  listener (`event: log`) for a page opened while the run is still executing, and a
  full-replay-from-`consoleLog` effect (`lib/logLine.ts`'s `parseLine` over the whole
  text at once) for a page loaded — or refreshed — **after** the run already finished,
  which the live-only path can never handle since `isLive` is false from the very first
  render in that case. This was a real, confirmed bug (checklist stuck on all-pending
  for an already-passed run) before the replay path was added.
- `api/client.ts` is the *only* place that calls `fetch`. It wraps every call in a
  `request<T>()` helper that throws `Error(body.error)` on non-2xx responses. New backend
  endpoints should get a corresponding method here rather than ad-hoc fetches in pages.
- `LogConsole.tsx` is the SSE consumer: opens `EventSource` on `/api/runs/{id}/stream`,
  listens for `log` and `done` named events, auto-scrolls unless the user has scrolled up
  more than ~60px. Used both live (RunTest) and passively (RunDetail's console tab, via
  `staticLog` when the run has already finished).
- Dev server (port 5173) proxies `/api/**` to `http://localhost:8080` (`vite.config.ts`) —
  no CORS issues in local dev; CORS is only relevant in prod/docker where frontend and
  backend are different origins (`CORS_ALLOWED_ORIGINS`).
- `types/index.ts` is a hand-written mirror of backend DTOs. There is no shared-types
  codegen — **if you change a backend DTO field, you must manually update this file and
  every frontend usage**, or the UI will silently show `undefined`.

## Design system

- Dark-only theme, tokens in `tailwind.config.js` (`base.*` surfaces/borders, `signal.*`
  semantic colors — brand/pass/fail/pending/skip — plus `ink.*` text tones). Component
  classes (`.glass-panel`, `.eyebrow`, `.console-scanlines`) live in `styles/index.css`.
  **Extend these tokens, don't fork them** — a new page/component should reuse
  `signal-brand`/`glass-panel`/`eyebrow` rather than inventing a parallel color or panel
  style.
- Deliberately restrained ("minimalistic but futuristic," per explicit direction):
  background is one subtle top-left glow plus a barely-visible fixed grid (not the
  original two competing gradient blobs); `shadow-glow` is reserved for the single
  primary action per view (Run button, sidebar mark) — pill/badge selection states use a
  solid `bg-signal-brand` fill instead of a glow, on purpose, to keep multi-badge views
  (History, Steps Explorer) from reading as busy.
- Motion follows the `animate` skill (emilkowalski/skills) philosophy: named transition
  properties only, never `transition-all` (grep clean as of this writing); custom easings
  `ease-out-strong` / `ease-inout-strong` in `tailwind.config.js` (`cubic-bezier(0.23, 1,
  0.32, 1)` / `cubic-bezier(0.77, 0, 0.175, 1)`) instead of Tailwind's weak built-ins;
  interactive-element durations in the 100–250ms range; a global
  `prefers-reduced-motion: reduce` rule in `styles/index.css` collapses all
  animation/transition durations to ~0. Deliberately *not* animated: per-tick MiniStat
  value updates during a live run (frequent-update tier — the skill's own gate calls for
  no motion here, not a missed opportunity).
- `components/FormControls.tsx`'s `Toggle` had a real, easy-to-reintroduce bug: the knob
  `<span>` had `top-[3px]` but no `left` value, so `translate-x-[21px]`/`translate-x-[3px]`
  were applied on top of an undefined base position — the knob rendered past the track's
  right edge, overlapping the label text. Fixed by giving the knob an explicit
  `left-[3px]` resting position and making the checked/unchecked classes pure
  `translate-x-0` / `translate-x-[18px]` deltas off of that. **If you touch this
  component again, verify both states by reading computed `getBoundingClientRect()` in a
  live browser, not just by eyeballing a screenshot** — this bug was invisible in casual
  code review and only surfaced by actually driving the app.

# Backend

- Spring Boot 3.3.4, Java 21 (Gradle toolchain), built with the Gradle wrapper
  (`./gradlew`) — no local Gradle install required.
- Classic controller → service → repository layering. Controllers are intentionally thin
  (see RunController, AttachmentController, StepExplorerController, TagController,
  DashboardController, EnvironmentController, ScenarioController, VisualDebugController)
  — no business logic lives there.
- Dynamic filtering (run status/tag/date-range, step-level search across every field) is
  implemented with Spring Data JPA `Specification<T>` composition in
  `repository/spec/*Specifications.java`, not query methods or native SQL in the
  controller. Follow this pattern when adding new filterable list endpoints.
- DTOs are separate types from JPA entities, each with a static `Dto.from(entity)` factory
  — entities never leave the service layer.
- `TestRunnerService` is the orchestration core: a single-threaded `ExecutorService`
  queue, a `ConcurrentHashMap<Long, Process>` of running processes for `cancel()`, and
  `ProcessBuilder` env-var mapping from the *resolved environment* (not the request) →
  engine env vars. See Core Architecture above for the full sequence. It exposes two
  entry points into the **same** queue and the **same** `executeRun(runId)`/
  `buildProcess(TestRun, reportDir)` — `enqueue(RunRequest)` (Standard) and
  `enqueueVisualDebug(VisualDebugRequest)` (Visual Debug); `buildProcess()` branches on
  `TestRun.executionMode` for the one thing that differs (how Cucumber is told what to
  run — `--tags` vs `CUCUMBER_TARGET`), not on two separate code paths. See Architectural
  Decisions for why Visual Debug still queues behind Standard runs rather than getting
  its own lane.
- `ScenarioCatalogService` enumerates every concrete scenario under `engine/features/**`
  by running Cucumber with `--dry-run` (no browser, no step/hook execution — see
  `engine/src/support/config.ts`'s module-load-time validation for why `HEADLESS=true`
  is still set even though nothing reads it in dry-run mode) into a scratch report path,
  then parses the resulting `cucumber.json` the same *shape* `CucumberJsonParserService`
  already understands, but into plain DTOs (`ScenarioCatalogEntryDto`), not JPA entities.
  Backs both `GET /api/scenarios` (the picker) and `TestRunnerService
  .enqueueVisualDebug()`'s validation (matches by `uri` + optional `line`) — both read
  the *same* live catalog, so they can't drift. Not routed through the run queue
  (dry-run touches none of the paths a real run does, safe to run concurrently with one).
  **Filters out Cucumber's synthetic `Before`/`After` hook entries** (they appear in the
  JSON `steps` array with no `name`) — a real bug caught during implementation: the
  Visual Debug step checklist advances by step *order*, and hooks.ts never logs
  `START`/`PASS`/`FAIL` for hooks (only `runLoggedStep`-wrapped DSL steps do), so
  including them would misalign every step after the first.
- `EnvironmentConfigService` resolves `RunRequest.environment` (e.g. `"QA"`) to a
  concrete `{baseUrl, apiBaseUrl}` pair by reading a committed, per-environment dotenv
  file, `<engine working dir>/.env.<name-lowercase>` (e.g. `engine/.env.qa`), the same
  way `FeatureTagScannerService` reads `engine/features/` (via
  `EngineProperties.workingDirectory` — no separate config property). It parses simple
  `KEY=VALUE` lines itself (no library — mirrors the tolerant, defensive style of
  `CucumberJsonParserService`/`FeatureTagScannerService`) and pulls out `BASE_URL`/
  `API_BASE_URL` directly — no interpolation, the files hold real hardcoded URLs.
  **`listEnvironments()` derives the entire environment list by scanning which
  `.env.<name>` files exist** under the engine directory — there is no separate registry
  to keep in sync; add an environment by adding a file. `.env.example` is explicitly
  excluded (it's the engine's own copy-to-`.env` template, not a real environment — this
  was a real bug caught during implementation, since it otherwise matches the naming
  pattern). `TestRunnerService.enqueue()` calls `resolve()` **before** creating the
  `TestRun` row, so an unknown/unconfigured environment returns a 400
  (`EnvironmentResolutionException` → `GlobalExceptionHandler`) instead of leaving a
  doomed `QUEUED` row. URLs never round-trip through the frontend or get exposed by
  `GET /api/environments` (name + label only, and label is currently just name — see
  Architectural Decisions).
- `CucumberJsonParserService` deliberately treats the input as untrusted/partial (its own
  doc comment: "intentionally defensive... because the report is produced by an external
  Node process") — missing fields, absent embeddings, and malformed JSON are handled by
  returning empty/default results, not by throwing. Preserve this defensiveness in any
  change to this parser. It is also the **source of truth for soft-assert step status**:
  a `Then` step run via `runLoggedAssertion` never throws (see engine Logging above), so
  Cucumber's own JSON always reports it as `passed` even when the assertion failed —
  `findSoftFailureLine()` scans the step's `text/plain` embedding for the exact
  `] ERROR FAIL ` marker that wrapper writes, and if present, overrides `StepResult`
  to `FAILED` with that line as the error message, regardless of what Cucumber said. It
  also filters out Cucumber's synthetic `Before`/`After` hook entries (`name == null`)
  from persisted `StepResult` rows the same way `ScenarioCatalogService` already did —
  their status still counts toward the scenario's overall worst-status, they're just not
  shown as a step row (this used to be a known gap here specifically; fixed alongside
  the soft-assert change since the new aggregated After-hook failure would otherwise
  have made the blank row much more common).
- `LogBroadcastService` keeps an in-memory rolling text buffer per run id so a client that
  connects to the SSE stream mid-run still sees everything emitted so far. Buffers/emitter
  lists are cleared when the run completes.
- `StaleRunCleanupRunner` (a `CommandLineRunner`) sweeps any `RUNNING`/`QUEUED` rows to
  `ERRORED` on JVM boot, because a backend restart mid-run leaves the DB row orphaned with
  nothing left alive to finish it.
- `GlobalExceptionHandler` is generic (`@ExceptionHandler(Exception.class)` returns a
  flat `{error, fields?}` JSON body) — there is no per-domain exception hierarchy.
- **No automated backend tests exist.** `backend/src/test` does not exist as a source
  directory (only empty Gradle build-output stubs under `backend/build/`). See Known
  Constraints.

# Test Engine

`engine/` is a standalone, reusable Playwright + Cucumber + TypeScript BDD framework —
read `engine/README.md` for its own (thorough) documentation. Key architectural point:
**it is designed so that writing a new test is (ideally) just a new `.feature` file plus
new locator YAML — not new step definitions.** The reusable DSL in `src/steps/*.steps.ts`
is intentionally small and generic (`I click "X"`, `I fill "X" with "Y"`, `"X" should be
visible`, `I hover over "X"`, `I double-click "X"`, `I go back`, `I clear cookies`,
`I take a screenshot`, `I store the text of "X" as "Y"`, `I generate a UUID as "X"`,
`I load file "X" as "Y"`, `I wait for "X" to be "<attached|detached|visible|hidden>"`,
`"X" should not contain "Y"`, `the numeric value of "X" should have changed by N from
"Y"`, `"X" should not have duplicate values`, `I open/use/close a new browser context
as "X"`, `I click "X" and expect a download`, `I wait for any of:` (DataTable of
aliases), `I wait for the text of "X" to change from "Y"`, `I retry up to N times
widening "X" and clicking "Y" until "Z" is visible`, `I skip the remaining steps if
"X" contains "Y"`, `I stop the scenario if "X" is not found`, `I fetch an OAuth2 token
as "X":` (DataTable of tokenUrl/clientId/clientSecret/grantType), etc.). Adding a
bespoke step definition for something the DSL can already express is against this
design — check `ui.steps.ts`/`api.steps.ts` first. This vocabulary was deliberately
grown to close gaps against a separate, unrelated project's YAML test framework
(`graphite-observer-ai`) as prep for a future *manual* migration of that project's
testcases to Cucumber — not an automated translator, and not code in this repo; see the
git history/session notes for that project's own action catalog if extending this list
further. **Deliberately not built in this pass** (explicit scope cut, not an oversight):
`dbQuery`/`dbPollUntil` (needs a real Oracle client and instance to build against and
verify — no way to do that safely in this environment; revisit once real DB connection
details exist) and a CDP-attach browser mode for SSO-gated environments (revisit once a
specific target environment is confirmed to need it — see Playwright section below).
`I skip the remaining steps if...`/`I stop the scenario if...` both work by returning
the literal string `"pending"` from the step function — a real, documented
`@cucumber/cucumber` convention (`step_runner.js`) that marks that one step PENDING
rather than PASSED/FAILED; Cucumber's own runner already treats any non-PASSED status as
a reason to skip a scenario's remaining steps, so this halts cleanly (shown as a
"Pending" warning, not a failure) without needing the soft-assert machinery at all.

- **Environment registry** (`engine/.env.<name>` — `.env.dev`, `.env.qa`, `.env.uat`,
  `.env.staging`, `.env.prod`): part of the engine's own core framework config, sitting
  alongside `.env`/`.env.example`/`framework.yaml`/`locators/` — but the engine process
  itself never reads these. It's the backend's `EnvironmentConfigService` that reads
  them (path derived from `EngineProperties.workingDirectory`, same as
  `FeatureTagScannerService` reads `engine/features/`), pulls `BASE_URL`/`API_BASE_URL`
  directly (real hardcoded values, no interpolation), and sets those on the engine child
  process — exactly the same two env vars `config.ts` already consumed before this
  existed. Unlike `.env` (git-ignored, holds credentials), these files **are committed**
  — target URLs for a test framework usually aren't secret. The set of files that exist
  *is* the environment list (`GET /api/environments` scans for them); adding a new
  environment is "add a file," no engine or frontend code changes. `.env.example` is
  excluded even though it matches the naming pattern — it's the copy-to-`.env` template,
  not an environment.
- **Locator registry** (`locator-registry.ts`): recursively loads every YAML file under
  `config/locators/` at import time into an in-memory `{PageName: {elementName: def}}`
  map. Aliases in feature files are `PageName.elementName` (e.g. `Login.email`).
  Supported strategies: `testId`, `role`, `label`, `text`, `placeholder`, `css`, `xpath`
  — the engine README explicitly recommends preferring `testId`/`role`/`label` for
  resilient tests over `css`/`xpath`.
- **World** (`world.ts`): per-scenario Cucumber World carrying `browser`, `context`,
  `page`, `api` (Playwright `APIRequestContext`), a `variables` Map for cross-step data,
  `requestHeaders`/`requestQuery` for API steps, and `softFailures`/`namedContexts`/
  `defaultContext` (see below). `this.context`/`this.page` always point at whichever
  browser context is currently "active" — `openContext`/`useContext`/`closeContext`
  (see Development Conventions → DSL vocabulary) mutate these two fields directly on
  switch rather than requiring every other step to resolve "the active context"
  indirectly, so the rest of the DSL (`ui.steps.ts`) needed zero changes to support
  multiple contexts per scenario. `namedContexts` holds any additional contexts opened
  via `openContext`; `defaultContext` lazily stashes the original scenario
  context/page the first time a scenario switches away from it, so `I use context
  "default"` can switch back.
- **Hooks** (`hooks.ts`): `BeforeAll` launches exactly one browser per Cucumber worker;
  `Before` creates a fresh, isolated `BrowserContext`+`Page` per scenario; `After` decides
  whether to keep the screenshot/video/trace based on the run's mode and whether the
  scenario failed, then closes the context; `AfterAll` closes the browser. This is the
  isolation boundary that makes parallel workers safe. `After` also closes any leftover
  `namedContexts`/stashed `defaultContext` best-effort (no artifact capture for those —
  only whichever context is active when the scenario ends gets a screenshot/trace/video),
  and — see Architectural Decisions — throws an aggregated error if `softFailures` is
  non-empty, since that's what actually fails a scenario that used soft-assert.
- **Auth** (`auth.ts`): UI auth signs in once per role per worker and caches Playwright
  `storageState` to `.auth/worker-<n>/<role>.json`; subsequent scenarios reuse it via
  `reuseOrAuthenticateUi` (which discards the pristine pre-auth context/video and swaps in
  an authenticated one). API auth (`applyApiAuthentication`) sets a Bearer token and/or
  `x-api-key` header from env vars named in `config/framework.yaml`'s `auth.roles`.
- **Config** (`config.ts`): loads `config/framework.yaml`, expands `${ENV_VAR}`
  placeholders, and validates/normalizes `browser.name` (falls back to `chromium`),
  `headless`, and the `screenshot`/`video`/`trace` mode enums — throws on invalid values
  rather than silently defaulting.
- **Logging** (`logger.ts`): every `Given`/`When` step is wrapped by `runLoggedStep`,
  which writes a START/PASS/FAIL+duration line via winston (colored console + JSON file
  per worker under `test-results/worker-<n>/logs/`) and **also attaches that same text
  as a `text/plain` Cucumber attachment on the step** — meaning every step of every
  scenario, not just failures, produces a Postgres `attachment` row after ingestion.
  Credentials/tokens are deliberately never logged. Every `Then` (assertion) step is
  wrapped by `runLoggedAssertion` instead — see "Soft-assert execution model" under
  Architectural Decisions for why these are two different functions with different
  failure behavior.

# Playwright

- Browsers: chromium / firefox / webkit, selected via `BROWSER` env, validated against an
  allow-list in `config.ts` (invalid/missing → `chromium`).
- One `Browser` instance per Cucumber worker (`BeforeAll`/`AfterAll`); one
  `BrowserContext` + `Page` per scenario (`Before`/`After`) — full isolation between
  scenarios, even within the same worker.
- Artifacts, each independently controllable via env var → `RunRequest` field:
  - `SCREENSHOT`: `off` | `on` | `only-on-failure` (default `only-on-failure`) — full-page
    PNG, captured in `After`.
  - `VIDEO`: `off` | `on` | `retain-on-failure` (default `off`) — recorded via the
    context's `recordVideo` option, then renamed into place or deleted post-hoc depending
    on outcome (Playwright always records if the option is set; the framework decides
    whether to keep the file).
  - `TRACE`: `off` | `on` | `retain-on-failure` (default `off`) — `context.tracing.start`
    in `createScenarioContext`, `context.tracing.stop` in `After`, with a `path` only when
    the trace should be kept.
- Screenshots are the only artifact type that flows into Postgres today (via Cucumber
  `embeddings` → `this.attach()`). Trace `.zip` and video `.webm` files are written to
  disk under `engine/test-results/worker-<n>/` but are **not** ingested into the database
  or exposed by any API — the README calls this out explicitly as an intentional v1 gap.

# Cucumber

- `@cucumber/cucumber` v11, config in `engine/cucumber.cjs` (CommonJS, loaded via
  `require`).
- Reporters: `progress-bar` (console), `html:<REPORT_DIR>/cucumber.html`,
  `json:<REPORT_DIR>/cucumber.json`. **The backend's `CucumberJsonParserService` parses
  the "legacy" Cucumber JSON formatter output** (per its own code comment) — an upstream
  Cucumber upgrade that changes or drops this formatter would silently break report
  ingestion. Verify the JSON shape after any `@cucumber/cucumber` version bump.
- `REPORT_DIR` (default `reports`), `PARALLEL_WORKERS` (→ `--parallel`), and
  `CUCUMBER_TARGET` are the env vars the platform injects per run; `retry` is hardcoded
  to `0` (no automatic retry of flaky scenarios anywhere in the stack).
- **`CUCUMBER_TARGET` overrides `paths` itself, not just adds to it — this matters.**
  `cucumber.cjs`'s `paths` defaults to `["features/**/*.feature"]`. A CLI positional
  scenario argument (`<uri>:<line>`) does **not** replace that — Cucumber merges CLI
  paths with the config's own `paths`, so passing one specific scenario on the command
  line while `paths` still matches everything runs the *entire suite*, not just that
  scenario. This was a real bug caught during Visual Debug validation (a "single
  scenario" request silently ran 4 scenarios from 3 different feature files). The fix:
  `cucumber.cjs` reads `CUCUMBER_TARGET` and, when set, uses `[CUCUMBER_TARGET]` as
  `paths` directly — `TestRunnerService.buildProcess()` sets this env var for
  `VISUAL_DEBUG` runs instead of passing a positional CLI argument. **Anyone touching
  Visual Debug's execution path should re-verify `totalScenarios === 1` after any
  cucumber.cjs or Cucumber-version change** — this is exactly the kind of thing that
  looks correct from the CLI docs and silently isn't.
- Tags (`@ui`, `@api`, `@demowebshop`, `@regression`, etc.) drive both scenario selection
  (`RunRequest.tagExpression` → `--tags`) and reporting rollups (`v_tag_failure_stats`,
  the Dashboard's `failuresByTag`). `GET /api/tags` discovers all distinct tags by
  regex-scanning `engine/features/**/*.feature` directly (not from run history), so newly
  added tags show up in the UI immediately, even before any run uses them.

# Test Execution Flow

See the diagram under **Core Architecture** — this section is intentionally not
duplicated. The one-sentence version: *Frontend → Backend queue → child process running
Cucumber+Playwright in `engine/` → cucumber.json on disk → backend parses & encrypts →
Postgres → Frontend reads back via REST, Grafana reads back via SQL views.*

# Database

- Postgres 15+ (16-alpine in docker-compose), schema owned entirely by **Flyway**
  (`spring.flyway.enabled=true`, migrations in `backend/src/main/resources/db/migration/`).
  `hibernate.ddl-auto=validate` — **Hibernate will refuse to start if the entities don't
  match the schema; it never mutates the schema itself.** Any entity change requires a new
  Flyway migration file (`V3__...sql`, etc.), never edits to `V1`/`V2`.
- Normalized core: `test_run` (1) → `feature_result` (N) → `scenario_result` (N) →
  `step_result` (N), plus `attachment` (N, FK → `scenario_result`). All child tables
  `ON DELETE CASCADE` from their parent.
- `V2__reporting_views.sql` adds five **read-only SQL views** that flatten this tree:
  - `v_scenario_detail`, `v_step_detail` — power `StepDetailView` (backend's Steps
    Explorer API) *and* are queried directly by Grafana. The migration's own comment
    explains why: keeping the flattening logic in SQL means both consumers "stay in sync
    automatically as new runs land, with no duplicated aggregation code." **Do not
    reimplement this flattening in Java or in a Grafana-specific query — extend the view.**
  - `v_run_daily_stats`, `v_tag_failure_stats`, `v_step_failure_stats` — pre-aggregated
    daily rollups, Grafana-only today.
- `StepDetailView.java` is a `@Entity @Immutable` JPA mapping directly onto
  `v_step_detail` — read-only, never written to via JPA (Hibernate would reject writes to
  an `@Immutable` view-backed entity anyway).
- `V3__add_environment_to_test_run.sql` adds `test_run.environment` and appends
  `run_environment` to `v_scenario_detail`/`v_step_detail` via `CREATE OR REPLACE VIEW`.
  **Postgres constraint to remember for any future view change**: `CREATE OR REPLACE
  VIEW` can only *append* trailing columns — it cannot reorder, rename, or remove
  existing ones, or the migration fails. That's why `run_environment` sits at the end of
  each SELECT list instead of next to the other `run_*` columns it conceptually belongs
  with. `StepDetailView.java` was **not** updated to map this new column (out of scope —
  the Steps Explorer UI doesn't show environment yet); it's available in Postgres/Grafana
  as a raw dimension only, for now.
- `V4__add_execution_mode_to_test_run.sql` adds `test_run.execution_mode` (default
  `'STANDARD'`), `scenario_uri`, `scenario_line` — all for Visual Debug. Deliberately
  does **not** touch `v_scenario_detail`/`v_step_detail`/Grafana (same "out of scope for
  now" reasoning as `V3`'s `run_environment` — the column exists for future use, nothing
  queries it yet). Every pre-`V4` `TestRun` row defaults to `execution_mode='STANDARD'`
  with `scenario_uri`/`scenario_line` null — History/Dashboard tolerate this without
  changes since they only ever *read* `RunSummaryDto.executionMode`, never assume it's
  set to something specific.

# Storage

- **Long-term/canonical storage is Postgres.** Screenshot bytes (and any other
  `this.attach(...)` data — currently also per-step text logs) are decoded from the
  Cucumber JSON's base64 `embeddings`, encrypted, and written to the `attachment.data
  BYTEA` column as part of the same transaction that persists the rest of the run.
- **On-disk engine storage is ephemeral/local, not part of the durable record**, with one
  important asymmetry:
  - `engine/reports/run-<id>/` *is* namespaced per backend run (via `REPORT_DIR`), so
    `cucumber.json`/`cucumber.html` for a given run stay put until manually cleaned.
  - `engine/test-results/worker-<n>/` (raw screenshots, videos, traces, per-worker logs)
    is namespaced **only by Cucumber worker id**, not by backend run id — the in-filename
    "run" counter (`scenarioSequence` in `hooks.ts`) is an in-process counter that resets
    every time the engine process starts, and is unrelated to the backend's `TestRun.id`.
    **Do not assume you can find "the video for run #42" on disk by run id** — see Known
    Constraints.
- `.env`, `node_modules`, `reports/`, `test-results/`, `.auth/` under `engine/` are
  git-ignored, as are `backend/build/` and `frontend/dist/`.

# APIs

All endpoints are under `/api`, defined across eight thin controllers (see Repository
Structure). Full reference (kept in sync with `README.md`, verified against controller
source):

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/runs` | Trigger a Standard run (`RunRequest` body: `environment`, `tagExpression`, browser/execution options — no raw URLs, see Architectural Decisions) |
| `POST` | `/api/visual-debug` | Trigger a Visual Debug run (`VisualDebugRequest`: `environment`, `scenarioUri`, `scenarioLine`) — rejects with 400 unless exactly one scenario matches; see Architectural Decisions |
| `POST` | `/api/runs/{id}/cancel` | Forcibly kill an in-progress run (both execution modes — same queue, same process handle) |
| `GET` | `/api/runs` | Paginated run history, filter by status/tag/date range |
| `GET` | `/api/runs/{id}` | Run detail + filtered scenario list — also how Visual Debug's dedicated view polls status (no separate GET endpoint exists for it) |
| `GET` | `/api/runs/{id}/stream` | SSE live console (`text/event-stream`, `log`/`done` events, replays backlog) — same stream Visual Debug's step checklist parses |
| `GET` | `/api/steps` | Cross-run, cross-feature step grid — the most heavily filterable endpoint |
| `GET` | `/api/attachments/{id}` | Decrypted screenshot/binary bytes |
| `GET` | `/api/scenarios/{id}/attachments` | Attachment metadata (id + mime type) only |
| `GET` | `/api/scenarios` | **Not** the same as the above — the full scenario catalog (every concrete scenario under `engine/features/`, via Cucumber `--dry-run`), backing the Visual Debug picker; see `ScenarioCatalogService` |
| `GET` | `/api/tags` | Distinct `@tags`, scanned live from `.feature` files |
| `GET` | `/api/environments` | Named environments (`name` + `label` only, never URLs) — see `EnvironmentConfigService` |
| `GET` | `/api/dashboard/summary` | Aggregate stats for Mission Control |

No authentication/authorization exists on any endpoint — see Known Constraints.

# Reporting

Two layers, both reading the same normalized data, deliberately kept from diverging:

1. **Steps Explorer** (`/explorer`, `GET /api/steps`) — every step from every scenario
   from every run ever recorded, in one paginated, richly-filterable grid, backed by
   `v_step_detail`.
2. **Dashboard** (`DashboardService`) — computed in Java (not SQL) over the 20 most
   recent runs: total/passed/failed/running counts, overall pass rate, failures-by-tag,
   and a pass-rate trend series. This is the one place aggregation logic lives outside
   SQL — `UNKNOWN / NEEDS VERIFICATION` why this wasn't also pushed into a view like the
   Grafana rollups; likely because it needs the *last 20 runs* window rather than a daily
   grouping, but this is not stated anywhere in the repo.

# Grafana

- Grafana OSS 11.2.0, provisioned entirely by file (`grafana/provisioning/`) —
  datasource (`postgres.yml`, points at the same Postgres, read-only role not enforced at
  the DB level — see Known Constraints) and a dashboard provider (`dashboards.yml`,
  `allowUiUpdates: true`, polls `grafana/dashboards/*.json` every 30s).
- Starter dashboard `test-ops-overview.json`: pass rate (stat + trend), run volume by
  outcome, total runs / failed scenarios / avg duration (stats), failures by tag (bar),
  step failure hotspots by keyword (bar), recent failed scenarios (table).
- Grafana queries Postgres **directly** — there is no backend API in this path. It reads
  the exact same `v_*` views the backend's Steps Explorer reads, so the two are
  guaranteed consistent.
- Grafana **cannot** render screenshots: attachment bytes are AES-256-GCM encrypted at
  rest and Grafana has no decryption key. This is a deliberate security boundary, not a
  missing feature — don't "fix" it by handing Grafana the key or a decryption proxy
  without discussing the security tradeoff with the user first.

# Logging and Observability

- **Engine**: winston, dual transport — colored/worker-prefixed console output, and
  structured JSON per-worker file logs (`test-results/worker-<n>/logs/worker-<n>.log`).
  Every DSL step additionally gets a START/PASS-or-FAIL+duration entry attached directly
  to its Cucumber report step (see Test Engine → Logging above). Credentials/tokens are
  deliberately excluded from all log output.
- **Backend**: SLF4J/Logback via Spring Boot defaults, `com.testplatform` package at
  `INFO` (`application.yml`). No structured/JSON logging, no external log shipping
  configured — `UNKNOWN / NEEDS VERIFICATION` whether anything ships backend logs
  anywhere in production; nothing in the repo suggests it does.
- **Live run visibility**: the backend does not "observe" the engine process beyond
  reading its combined stdout/stderr (`redirectErrorStream(true)`) line by line — there
  is no structured event protocol between engine and backend, just text scraped for
  storage/replay and eventually the process exit code.
- **Persisted execution history** (the actual observability data model): `TestRun` →
  `FeatureResult` → `ScenarioResult` → `StepResult` → `Attachment`, queryable via the
  Steps Explorer grid and visualized in Grafana. This is the system's real observability
  backbone, not application logs.

# Configuration

Three independent configuration surfaces — do not confuse them:

1. **`engine/.env`** (git-ignored, copy from `engine/.env.example`) — used when running
   the engine standalone (`npm test`). Documents: `BASE_URL`, `API_BASE_URL`, `HEADLESS`,
   `SCREENSHOT`, `VIDEO`, `TRACE`, `PARALLEL_WORKERS`, plus per-role credential env vars
   (`ADMIN_USERNAME`, `ADMIN_PASSWORD`, `ADMIN_BEARER_TOKEN`, `ADMIN_API_KEY`,
   `MEMBER_USERNAME`, `MEMBER_PASSWORD`, `MEMBER_BEARER_TOKEN`). When the backend spawns
   the engine, it sets `BASE_URL`/`API_BASE_URL` itself from the resolved environment
   (see item 2) and the rest directly from `RunRequest` (see `TestRunnerService
   .buildProcess`) — `.env` is a fallback/standalone-use path, not what a
   backend-triggered run relies on. Auth credentials still come from `.env` (or CI
   secrets) either way, since `RunRequest` has no credential fields, and never did.
2. **`engine/.env.<name>`** (`.env.dev`, `.env.qa`, `.env.uat`, `.env.staging`,
   `.env.prod`) — **committed** (unlike `.env`), one file per named environment, each
   holding real hardcoded `BASE_URL`/`API_BASE_URL` values. Read only by the backend's
   `EnvironmentConfigService`; the engine process never sees these files. This is the
   single source of truth for "which environments exist" — the file list *is* the
   registry, nothing else declares it. Alongside `engine/config/framework.yaml` +
   `engine/config/locators/*.yaml` (browser defaults, auth role → env-var-name mapping,
   locator aliases — also checked into git, secrets there are only ever *names* of env
   vars, never values). **`RunRequest` no longer accepts raw `baseUrl`/`apiBaseUrl` at
   all** — the frontend sends an `environment` name (`"QA"`) and the backend resolves it
   from the matching `.env.<name>` file; see Architectural Decisions.
3. **`backend/src/main/resources/application.yml`** — Spring config, itself sourcing most
   values from env vars with sensible local defaults: `DB_HOST/PORT/NAME/USER/PASSWORD`,
   `ENGINE_DIR` (default `../engine`), `ENGINE_COMMAND` (default `npm test --`),
   `ENGINE_TIMEOUT_MINUTES` (default 30), `CORS_ALLOWED_ORIGINS`,
   `ATTACHMENT_ENCRYPTION_KEY` (default is an **insecure placeholder** — must be
   overridden in any shared/production environment). No per-environment URL config lives
   here — that's entirely item 2.

Frontend has no runtime env config of its own beyond the Vite dev-server proxy target
(hardcoded to `localhost:8080` in `vite.config.ts`) — it always talks to `/api` relative
to whatever origin served it.

# Development Conventions

- **Backend**: controller → service → repository; DTOs with static `from(entity)`
  factories; dynamic query filtering via JPA `Specification<T>` composables in
  `repository/spec/`, not ad-hoc `@Query` strings or in-controller filtering logic.
  Config classes use `@ConfigurationProperties` (`EngineProperties`) rather than scattered
  `@Value` injections where there's more than one or two related settings.
- **Database**: schema changes ONLY via new Flyway migration files; never hand-edit
  `V1`/`V2`; never rely on Hibernate DDL auto-generation (`ddl-auto=validate` will just
  fail startup if entities and schema disagree).
- **Frontend**: one `api` object as the sole HTTP boundary; pages own their own data
  fetching (`useEffect` + local state), no global state management library in use; typed
  contracts hand-mirrored from backend DTOs in `types/index.ts`.
- **Engine / step definitions**: prefer expressing new test coverage as `.feature` +
  locator YAML over new step definitions. The existing DSL in `ui.steps.ts`/`api.steps.ts`
  is meant to be sufficient for "standard interactions" (the engine README's own words).
  Only add a new step definition when the existing DSL genuinely cannot express the
  interaction.
- **Locators**: prefer `testId` / `role` / `label` strategies over `css`/`xpath` (engine
  README's explicit recommendation, though the shipped `demowebshop` example locators are
  mostly `css` because they target a third-party demo site the framework doesn't control).
- **Secrets**: never in YAML/JSON config — only ever env-var *names* in
  `framework.yaml`/`application.yml`, actual values via `.env` (engine, git-ignored) or
  process environment (backend/docker-compose).
- **Artifacts as data, not files**: the platform's design bias is to decode/normalize
  execution artifacts into Postgres (screenshots, step logs) rather than serve raw files
  off disk — keep this bias in mind if extending reporting; a "list files in
  reportDirectory" feature was explicitly deferred (README) rather than being the default
  approach.

# Architectural Decisions

**Single-threaded run queue (one engine process at a time).**
What: `TestRunnerService` uses a single-threaded `ExecutorService`; a `QUEUED` run waits
for the current one to finish.
Why: all runs share one `engine/` checkout — concurrent processes would race on
`node_modules` and (pre-`REPORT_DIR`) report files.
Depends on it: `runningProcesses` map for `cancel()`, `StaleRunCleanupRunner`'s assumption
that a fresh boot never has a genuinely-in-progress run, the UI's "queued vs running"
status model.
Do not change casually: making runs concurrent requires either multiple engine checkouts
or a redesign of report-path isolation beyond just `REPORT_DIR`, plus rethinking `cancel`
(which currently keys on a single process per run id, which already works fine
concurrently — the actual blocker is the shared checkout, not the Java code).

**Attachments encrypted at rest (AES-256-GCM, PBKDF2-derived key).**
What: every `this.attach(...)` payload (screenshots, per-step text logs) is encrypted
before hitting Postgres; decrypted on demand by `AttachmentController`.
Why: screenshots can contain sensitive UI content; stated explicitly in README/code
comments as a deliberate security measure, not incidental.
Depends on it: `ATTACHMENT_ENCRYPTION_KEY` — changing this key **permanently orphans**
previously-stored attachments (by design, per README: "treat it like a database
password").
Do not change casually: don't add a "master key" bypass, don't log the key or plaintext
key material, don't give Grafana or any other consumer the key just to enable a feature —
this boundary is intentional (see Grafana section).

**SQL views as the single flattening layer, shared by two consumers.**
What: `v_scenario_detail`/`v_step_detail`/`v_run_daily_stats`/`v_tag_failure_stats`/
`v_step_failure_stats` in `V2__reporting_views.sql`.
Why: migration's own comment — keeps Steps Explorer and Grafana "always looking at
identical data" with "no duplicated aggregation code."
Depends on it: `StepDetailView` JPA entity (`@Immutable`, mapped straight onto the view),
every Grafana panel in `test-ops-overview.json`.
Do not change casually: adding a new cross-cutting rollup should almost always be a new
view (or a new migration altering an existing one), not duplicated logic in
`DashboardService` or a Grafana-only SQL query pasted into a panel.

**Engine treated as an external, only-lightly-patched dependency.**
What: only two *behavioral* changes were made to accommodate the platform —
`REPORT_DIR` support in `cucumber.cjs`, and `BROWSER` env support in
`framework.yaml`/`config.ts`. Everything else (hooks, steps, locators, world) is stated
as untouched. Environment-based execution (see the new decision below) added new config
*files* (`engine/.env.dev`, `.env.qa`, `.env.uat`, `.env.staging`, `.env.prod`) but zero
engine *code* changes — the engine process still only ever reads `BASE_URL`/
`API_BASE_URL`, exactly as before; it has no idea "environments" exist as a concept.
Why: preserves the engine's standalone usability (`npm test` still works unmodified
outside the platform) and minimizes the blast radius of the orchestration layer on a
test framework that has its own independent value.
Depends on it: the README's explicit backward-compatibility claim.
Do not change casually: prefer new, additive env vars over modifying existing engine
behavior when extending orchestration; if the engine needs a real behavioral change,
call it out clearly rather than letting it drift silently out of sync with
`engine/README.md`'s own description of itself.

**No auth anywhere (v1, explicit scope decision).**
What: no login on the API, the frontend, or (beyond Grafana's own admin/admin) Grafana.
Why: stated explicitly in README as "intentionally out of scope for v1."
Depends on it: nothing architecturally — this is a known gap, not a load-bearing
decision.
Do not change casually in the other direction either: don't add auth unprompted, since
it's a deliberate, acknowledged scope cut, not an oversight — but do flag it if the user's
request would expose this deployment beyond a trusted local network.

**Environment is a first-class, backend-resolved concept — frontend and engine never
see raw URLs.**
What: the frontend sends `RunRequest.environment` (a name like `"QA"`), never
`baseUrl`/`apiBaseUrl` (those fields were removed from `RunRequest` entirely).
`TestRunnerService.enqueue()` calls `EnvironmentConfigService.resolve()` before creating
any `TestRun` row; the resolved `{baseUrl, apiBaseUrl}` is what actually reaches the
engine child process. `GET /api/environments` exposes only `{name, label}` pairs (label
currently just equals name) — never the resolved URLs — so there is no path by which a
browser client can observe or override a real environment URL.
Why: requested explicitly — "the frontend should send `environment: QA`... rather than
requiring the frontend to send `uiUrl`/`apiUrl`" — plus a single source of truth for
environment definitions instead of duplicating URLs across frontend/backend/engine.
Source-of-truth mechanism went through two iterations this session, both worth knowing
about if you're wondering "why not X": first a repo-root `config/environments.yaml`
(rejected — didn't reflect that this is an engine-framework concern), then a single
`engine/config/environments.yaml` with `${VAR}`-interpolated placeholders resolved
against the backend's own env (rejected in favor of the current design once the user
said "this is a test framework, I'd rather hardcode the URLs... switch to .env files").
**Current design**: one committed file per environment, `engine/.env.<name-lowercase>`,
holding real hardcoded `BASE_URL`/`API_BASE_URL` — no interpolation, no separate backend
env vars to set. `EnvironmentConfigService.listEnvironments()` derives the whole
environment list by scanning for `.env.<name>` files, so **the file list is the
registry** — there is no second place a name is declared. `.env.example` is explicitly
excluded despite matching the naming pattern (it's the engine's own copy-to-`.env`
template) — this was a real bug caught and fixed during implementation, worth
remembering if the exclusion list ever needs to grow.
Depends on it: `RunRequest`/`RunSummaryDto`/`TestRun.environment` (new column, `V3`
migration), `EnvironmentConfigService`, `EnvironmentPicker.tsx`. Environments are
scaffolded (`DEV`/`QA`/`UAT`/`STAGING`/`PROD` — one `.env.<name>` file each) but mostly
**unconfigured by default** (`BASE_URL`/`API_BASE_URL` blank) — a run against one fails
fast with a clear 400 (`EnvironmentResolutionException`) until both are filled in
directly in that file. `.env.dev` already has a real `BASE_URL` filled in (the same demo
site used elsewhere in this repo); its `API_BASE_URL` and all of QA/UAT/STAGING/PROD are
still blank pending real values — not invented, per explicit instruction.
Do not change casually: don't reintroduce a `baseUrl`/`apiBaseUrl` field on `RunRequest`
as a "quick override" escape hatch — that's exactly the coupling this decision removed.
New environments are added by adding a new `engine/.env.<name>` file, nothing else; don't
reintroduce a separate registry file or duplicate a URL list anywhere else. Because these
files are committed (not git-ignored like `.env`), never put credentials or tokens in
them — URLs only, exactly like `engine/.env.example` already models.

**Product rename is display-only — internal identifiers untouched.**
What: the user-facing product name is **"AI-Powered Test Automation & Intelligence"**
(browser tab title, sidebar brand lockup, `README.md`/`CLAUDE.md` titles). The backend
Java package (`com.testplatform`), Gradle/npm artifact names (`test-orchestrator`,
`test-orchestrator-ui`), Docker container names, and the Postgres database name
(`test_platform`) were explicitly left alone.
Why: the request was to rename the app "a little better even in ui" — read as a
branding/display change, not a mandate to rename every internal identifier. A full
identifier rename touches Java package declarations, Gradle build config, Docker
Compose service names, and a live Postgres database name — real risk (import breakage,
container/volume name mismatches, a database rename requiring a migration or manual
`ALTER DATABASE`) for a request that was about what the *user* sees, not internal
plumbing.
Depends on it: nothing else assumes internal names match the product name — they never
did (the original name was "Test Ops Console" in the UI while the package was already
`com.testplatform`).
Do not change casually: if a future request explicitly asks to rename the package/
artifacts/database too, treat that as a separate, larger, higher-risk task — flag the
blast radius (recompilation, Docker image rebuild, a real data-bearing database rename)
before doing it, don't fold it silently into a UI request.

**Visual Debug: one scenario, resolved against a live catalog, sharing the existing
queue — live browser video deliberately deferred.**
What: a second execution mode (`ExecutionMode.VISUAL_DEBUG` on `TestRun`) alongside
Standard. The frontend never sends a tag expression or a multi-select for this mode —
`ScenarioPicker` is a single-select radio group sourced from `GET /api/scenarios`
(`ScenarioCatalogService`, a Cucumber `--dry-run` enumeration of every concrete
scenario). The backend independently re-validates against the *same* live catalog
before creating any `TestRun` row or spawning any process (`TestRunnerService
.enqueueVisualDebug()`) — 0 matches → "not found," >1 matches → the specified
multi-match message, both as `VisualDebugValidationException` → 400. Browser
(chromium), headless (`true`), and parallel workers (`1`) are forced server-side, never
accepted from the client. Visual Debug runs go through the **same** single-threaded
`runQueue` as Standard runs — no separate execution lane — because the underlying
constraint (one engine process at a time against the shared checkout) applies equally
to both; giving Visual Debug its own lane would need a second engine checkout, which is
out of scope.
Why: requested explicitly, with the constraint stated up front — "the exact streaming
implementation should be determined after inspecting the existing architecture" and,
after evaluating VNC/noVNC/WebRTC against this repo's actual deployment model (backend
and engine already share a process boundary — see the "Engine treated as an external,
only-lightly-patched dependency" decision above), **live browser video/frame streaming
was explicitly descoped by the user for this pass** ("live browser streaming part you
can ignore for now"). The recommended future path (Chrome DevTools Protocol screencast
over the existing SSE stream, no new infrastructure) is documented in full in
`VisualDebugView.tsx`'s comments and was deliberately left as a labeled placeholder
panel in the UI rather than built.
Depends on it: `ScenarioCatalogService` (also used by nothing else today — if it starts
being used elsewhere, keep its dry-run/no-queue characteristics in mind, see Test
Engine), the `V4` migration's `execution_mode`/`scenario_uri`/`scenario_line` columns,
`cucumber.cjs`'s `CUCUMBER_TARGET` handling (see Cucumber section — this was a real bug,
not just a design choice, and is easy to reintroduce if `buildProcess()` is refactored
to pass a positional CLI arg again "for simplicity").
Do not change casually: don't let Visual Debug's request contract grow a tag-expression
or multi-scenario option — the single-scenario guarantee is the entire point, enforced
in two independent places (picker UX + backend catalog re-check) on purpose. Don't
build live streaming without re-reading this decision's reasoning first — VNC/WebRTC
were rejected for concrete, repo-specific reasons, not just because they were more
effort.

**Parallel-run log differentiation is a frontend parsing/rendering change only.**
What: `components/LogConsole.tsx` (used by Standard execution's `RunTest`/`RunDetail`)
and `lib/logLine.ts` (the shared parser, also used by `VisualDebugView`'s step
checklist) strip ANSI codes and parse the existing `HH:mm:ss.SSS [W<id>]
[<scenario>] LEVEL message` line shape into worker-badged, severity-colored,
scenario-labeled rows, plus a "group by worker" collapsible view and a worker filter.
Two independent color systems: a new small palette (`WORKER_PALETTE` in
`LogConsole.tsx`) for worker identity, deliberately distinct from the existing
`signal.*` semantic colors, which severity continues to reuse (`signal-fail`=ERROR,
`signal-pending`=WARN) — never the same color mechanism for both, per explicit
requirement.
Why: worker identity was **already propagated end-to-end** before this change —
`logger.ts` has always prefixed every console line with `[W<id>]` — it just never
survived the trip to the browser usably: those lines carry raw ANSI color escapes
(meant for a terminal) into a plain `<div>`, and nothing on the frontend parsed the
`[W<id>]` prefix at all. Confirmed directly from a real run's persisted `consoleLog`,
not assumed. Fixing it at the presentation layer — not by changing the SSE transport or
engine logging — is "the smallest clean change necessary," per explicit instruction not
to introduce a second real-time transport.
Depends on it: the exact line format `logger.ts` produces. If that format ever changes
(field order, added fields), `STRUCTURED_PATTERN` in `lib/logLine.ts` needs updating
too, or every line silently falls back to unstructured plain rendering (safe failure
mode — never crashes, just loses the worker/severity/scenario treatment).
Do not change casually: the regex is deliberately **not** anchored to the start of the
line (`^` was removed) — Cucumber's own "progress" formatter writes an un-terminated
`.`/`F` character with no trailing newline immediately before some log lines (most
consequentially on FAILED steps, exactly where the worker badge matters most), which
the backend's line-by-line stdout reader concatenates onto the front of the next line.
This was a real bug, caught only by actually triggering a multi-worker run and reading
the rendered output — re-anchoring this regex "for correctness" would silently break
worker-badging on every failure line again.

**Soft-assert execution model for `Then` (assertion) steps — engine-wide, `Given`/`When`
unaffected.**
What: every `Then` step runs via `logger.ts`'s `runLoggedAssertion` instead of
`runLoggedStep`. On failure it logs/attaches `FAIL ...` exactly like before but does
**not** throw — it pushes the failure onto `world.softFailures` (`TestWorld`) and
returns, so Cucumber keeps invoking the scenario's remaining steps instead of skipping
them. `hooks.ts`'s `After` hook throws one aggregated error at the very end (after all
existing screenshot/trace/video capture, which now also treats `softFailures.length > 0`
as "failed" for on-failure artifact modes) if any were recorded, which is what actually
flips the scenario to FAILED — nothing else will, since no step itself threw.
`Given`/`When` (action) steps are untouched — `runLoggedStep` still throws and still
halts the scenario immediately on a broken click/fill/navigate/etc.
Why: requested explicitly, scoped down from "all failures are soft" to assertion-only
after discussing the risk of continuing past a broken *action* into steps that assume
it succeeded — soft-asserted steps are read-only checks, so they can't leave the page in
a state that makes a later step meaningless the way a failed click could.
**The real design constraint, worth remembering before touching this again**:
Cucumber.js's own `TestCaseRunner` derives a step's status purely from whether it threw,
and once a step throws it does not invoke the scenario's remaining steps — this is
internal runtime behavior with no supported override. So "keep running every `Then`
step past a failure" and "have Cucumber's own JSON mark that step FAILED" are mutually
exclusive if you rely on Cucumber's native status alone. The resolution moves the
source of truth for step status to the backend instead of Cucumber's JSON — see
`CucumberJsonParserService`'s `findSoftFailureLine()` under Backend above, which
overrides a step's status to FAILED if its `text/plain` attachment contains the
`] ERROR FAIL ` marker `runLoggedAssertion` writes, regardless of what Cucumber
reported. Verified live end-to-end (not just by reading the code): a scratch scenario
with 3 of 4 `Then` steps intentionally failing showed all 4 steps executing, Cucumber's
own JSON reporting all 4 as `passed`, and `GET /api/runs/{id}` correctly showing the 3
that failed as `FAILED` with real error messages and the scenario as `FAILED` overall —
while a separate scratch scenario with a broken `When` step confirmed action failures
still skip the remaining steps exactly as before.
Depends on it: `CucumberJsonParserService`'s embedding-scan override is coupled to the
exact log-line format `writeLog`/`runLoggedAssertion` produce — if that format changes,
`findSoftFailureLine()`'s `] ERROR FAIL ` marker needs updating too, or soft-failed
steps silently stop showing as failed in the UI (they'd still fail the *scenario*
correctly via the After-hook throw, just without per-step detail).
Do not change casually: this applies to every scenario in the repo today, not opt-in
via a tag — an existing scenario with multiple sequential `Then` steps where an earlier
one fails now runs all of them instead of skipping the rest, which is an intentional,
explicit choice, not an oversight. Don't extend soft-assert to `Given`/`When` steps
without re-deriving whether that's safe for the specific action — the read-only-checks
reasoning above doesn't hold for state-mutating steps.

# AI Development Operating Rules

Follow this workflow for every non-trivial task in this repository:

1. **Understand the requested change** — restate it in terms of this repo's actual
   modules (which of engine/backend/frontend/grafana does it touch?).
2. **Inspect relevant existing code** before writing anything — this repo has strong,
   consistent conventions (Specification-pattern filtering, DTO factories, the locator
   registry, the SQL-views-not-duplicated-logic rule); find the existing pattern before
   inventing a new one.
3. **Identify dependencies and callers** — e.g. before touching `CucumberJsonParserService`,
   check what depends on its output shape (`TestRunnerService.finalizeRun`, every DTO
   downstream); before touching a DTO field, grep `frontend/src/types/index.ts` and every
   usage site, since there's no shared-types codegen to catch drift for you.
4. **Explain the proposed approach when the change is significant** — especially anything
   that crosses the engine/backend boundary (env vars, report format), touches the DB
   schema, or touches the encryption boundary.
5. **Make the smallest appropriate change** — this codebase is small and consistent by
   design; resist adding abstraction layers, new dependencies, or config surfaces beyond
   what's asked.
6. **Validate the change** — see Validation and Testing below (there is no test suite to
   run automatically; validation is manual/targeted).
7. **Check for regressions** — specifically: does this change the shape of
   `cucumber.json` parsing, a DTO/API contract, or the SQL views Grafana depends on?
8. **Summarize exactly what changed** — file paths, and which of engine/backend/frontend/
   grafana/db were touched.

For larger changes: **first understand, then propose, then implement, then test, then
verify.** Do not blindly modify files based only on the user's first description — this
repo has enough cross-module coupling (env var contracts, DTO mirrors, SQL views feeding
two consumers) that an under-specified change is likely to break something non-obvious.

Specific things to always check before changing shared surfaces:
- **Before changing a DTO**: grep every controller that returns it, and
  `frontend/src/types/index.ts` + every frontend usage.
- **Before changing the DB schema**: write a new Flyway migration; check whether
  `v_scenario_detail`/`v_step_detail`/the daily-stats views need a matching change, and
  whether `StepDetailView.java`'s field list needs to match.
- **Before changing engine env vars or `cucumber.cjs`**: check
  `TestRunnerService.buildProcess()` (backend side) and `engine/.env.example`
  (documentation) both stay in sync.
- **Before changing `CucumberJsonParserService`**: confirm against an actual
  `cucumber.json` sample (e.g. one under `engine/reports/run-12/` if present) rather than
  assumptions about the format.
- **Before changing anything under `AttachmentCipher`/`ATTACHMENT_ENCRYPTION_KEY`
  handling**: this is a security boundary with a documented "changing the key orphans old
  data" tradeoff — don't change key derivation, IV handling, or the encrypt/decrypt
  contract without flagging the compatibility impact to the user explicitly.

# AI / Agent Architecture

The project has **no AI/agent code today**. This section documents where such
capability could plug in, based on what data already exists — it is analysis, not a
design commitment.

Natural integration points, in order of how directly they map onto existing seams:

1. **Post-run analysis agent** — a new backend service (parallel to `DashboardService`)
   or an external consumer of `GET /api/steps` / `GET /api/runs/{id}` that runs after
   `TestRunnerService.finalizeRun()` persists a run, and produces a summary/classification
   of what failed and why. The natural hook point is right after
   `finalizeRun`'s `testRunRepository.save(run)` — an event or async call could be added
   there without touching the parsing/persistence logic itself.
2. **Failure-analysis agent** — consumes exactly what `StepResult.errorMessage` +
   attached screenshots (`Attachment`, decrypted via `AttachmentCipher`) + the per-step
   text/plain execution log (already attached by `logger.ts`'s `runLoggedStep` on *every*
   step, not just failures) already provide per failed step. This triple — error message,
   screenshot, structured step log — is richer than most CI failure output and is already
   flowing into Postgres today with zero additional instrumentation needed.
3. **Self-healing locator agent** — the locator registry (`config/locators/*.yaml`) is
   the natural target: it's a flat, declarative, git-tracked mapping from alias → CSS/
   role/testId selector, completely decoupled from step definitions and feature files. A
   healing agent proposing "this selector broke, here's a replacement" only ever needs to
   propose a diff to one YAML file — it never touches `.feature` files or step
   TypeScript. This is the single most tractable healing target in the codebase.

# Self-Healing Test Architecture

**Not implemented.** The sections below are an analysis of what already exists to build
on, and are explicitly scoped to architecture/data-availability, not a design or
implementation plan.

**What data is already available when a test fails**, without any new instrumentation:
- Structured failure info: `StepResult.errorMessage`, `ScenarioResult.errorMessage`
  (concatenation of all failed step errors), `ExecutionStatus` per step and scenario.
- **Screenshots**: yes — full-page PNG on failure by default (`SCREENSHOT=only-on-failure`
  is the framework default), captured in `hooks.ts`'s `After`, stored encrypted in
  Postgres, retrievable via `GET /api/attachments/{id}`.
- **Playwright traces**: only if the run was configured with `TRACE=on` or
  `retain-on-failure` (default is `off`). When present, they land as `.zip` files on disk
  under `engine/test-results/worker-<n>/` — **not ingested into Postgres, not exposed via
  any API today.** A self-healing/analysis agent wanting trace data would need to either
  (a) read the file directly off the backend host's filesystem using
  `reportDirectory`/worker-directory naming, which is fragile per the run-id-namespacing
  gap noted in Storage, or (b) the platform would need a new endpoint to serve/ingest
  traces (the README already suggests `GET /api/runs/{id}/artifacts` as a natural
  follow-up).
- **Browser/DOM information**: not captured directly (no DOM snapshot/HTML dump step
  exists in the DSL today). Playwright traces (when enabled) contain DOM snapshots
  internally, but per above, traces aren't currently surfaced anywhere. Adding a DOM
  snapshot on failure would be a `hooks.ts` `After` addition, analogous to the existing
  screenshot capture.
- **Console/network logs**: not captured today. No `page.on('console', ...)` or
  `page.on('request'/'response', ...)` listener exists anywhere in `hooks.ts` or
  `browser-runtime.ts`. This would be new instrumentation, not something already flowing.
- **Cucumber scenario/step information**: yes, fully — feature name, scenario name,
  tags, step keyword/text/order/duration/status, all normalized in Postgres and queryable
  via the Steps Explorer view (`v_step_detail`).
- **Per-step execution logs**: yes — every step (pass or fail) gets a structured
  START/PASS-or-FAIL+duration text attachment (see `logger.ts`), already in Postgres as
  an `attachment` row with `mime_type=text/plain`.

**Where test results are stored:** Postgres, normalized
(`test_run`→`feature_result`→`scenario_result`→`step_result`) plus `attachment`, per
Database section above. This is also the natural place healing-related data would live.

**Where healing results could be stored:** no existing table for this. Would need a new
Flyway migration — most natural shape, given the "locators are the tractable healing
target" analysis above, is something like a `locator_healing_suggestion` table
(alias, old definition, proposed definition, evidence — scenario/step id, screenshot id
— status: proposed/approved/rejected/applied), separate from the append-only
`test_run`/`scenario_result` execution history so healing workflow state doesn't
contaminate the execution record.

**Where human approval could be introduced:** the frontend already has the UI
scaffolding pattern for this — a new page analogous to `StepsExplorer.tsx` (a filterable
grid) showing pending healing suggestions with an approve/reject action, calling new
backend endpoints. The existing `RunDetail`/`ScenarioGrid` pattern of showing evidence
(error text + screenshot) alongside a decision point is directly reusable.

**How proposed fixes could be validated:** the existing `POST /api/runs` trigger path
already supports scoping a run by tag expression — a validation flow could apply a
proposed locator change to a scratch copy of `config/locators/*.yaml`, trigger a
narrowly-tagged run (or a single scenario) against it, and only mark the suggestion
"validated" if that run passes. This reuses the existing run-and-parse pipeline
end-to-end rather than requiring new execution infrastructure.

**How incorrect AI-generated fixes could be prevented from reaching production:**
`config/locators/*.yaml` is git-tracked — the natural safety boundary is that no healing
agent should ever write directly to these files; it should propose a diff that a human
approves (see above) and that then goes through normal git review, exactly like any other
code change. The single-run-at-a-time queue and the tag-scoped validation run described
above also mean a bad automated fix can be validated in isolation before ever touching the
full suite.

**What information would be useful to an agent but is currently missing:**
- Playwright traces and DOM snapshots ingested/exposed the same way screenshots are.
- Browser console and network logs per scenario.
- A stable link between the on-disk `test-results/worker-<n>/` artifacts and the backend
  `TestRun.id` (currently only the in-process `scenarioSequence` counter, which is not
  run-scoped — see Storage).
- Historical "this locator alias has failed N times across M runs" — derivable today from
  existing tables/views via a query, but not materialized as its own view yet; would be a
  natural `V3` migration companion to `v_tag_failure_stats`/`v_step_failure_stats`.

# Safety Rules for Automated Changes

- Never write directly to `config/locators/*.yaml`, `.feature` files, or step definitions
  as an automated "fix" without human review — these are the test's source of truth and
  changing them silently changes what's actually being verified.
- Never change `ATTACHMENT_ENCRYPTION_KEY` handling, key derivation, or the encrypt/
  decrypt contract without explicitly flagging the "old attachments become permanently
  unreadable" consequence to the user first.
- Never hand-edit `V1__init_schema.sql` or `V2__reporting_views.sql` — always add a new
  migration.
- Never bypass the single-run-queue design to "speed things up" without discussing the
  shared-checkout race condition it exists to prevent.
- Never commit real credentials, tokens, or a non-placeholder
  `ATTACHMENT_ENCRYPTION_KEY` value into any tracked file — `engine/.env` and any
  production secret values are git-ignored/environment-only by design.
- Never assume the on-disk `engine/test-results/worker-<n>/` contents for "the last run"
  are attributable to a specific `TestRun.id` — that directory is not run-scoped (see
  Storage). Use Postgres as the source of truth for anything historical.

# Validation and Testing

**There is no automated test suite for the platform itself** (backend has no
`src/test`, frontend has no test runner configured, `engine/` has BDD *feature* files but
these test a third-party demo site, not the platform's own code). Validation today is
manual:

- **Backend**: `./gradlew build`/`./gradlew bootRun` as documented in the README, **but
  no `gradlew`/`gradlew.bat` wrapper script actually exists anywhere in this repo**
  (verified — not even gitignored, just never committed). Use a system-installed
  `gradle` instead (`cd backend && gradle build`/`gradle compileJava`) — confirmed
  working against this project's `build.gradle` (Spring Boot 3.3.4 / Java 21 toolchain).
  See Known Issues.
- **Frontend**: `cd frontend && npm run build` (TypeScript project-reference build via
  `tsc -b` + Vite build) is the real type-safety check and works cleanly. `npm run lint`
  is defined in `package.json` but **`eslint` is not listed in `devDependencies` and
  isn't installed** — the script fails with `eslint: command not found`. See Known
  Issues. `npm run dev` for manual UI verification.
- **Engine**: `cd engine && npm run typecheck` (`tsc --noEmit`) is the only "test" in the
  traditional sense. `npm test` / `npm run test:ui` / `npm run test:api` actually execute
  the BDD suite against whatever `BASE_URL`/`API_BASE_URL` is configured — running these
  exercises real network calls against a real (demo) application, not a mock.
- **End-to-end**: `docker compose up --build` is the closest thing to an integration
  check — it builds all three images and wires them together with real Postgres/Grafana.

When making a change, validate at the layer(s) actually touched — there is no single
"run everything" command, and given the above, **do not claim a change is "tested"
without having actually run the relevant build/typecheck/lint or manually exercised the
affected UI flow in a browser**, per this project's general instructions on UI changes.

**Demonstrated concretely this session**: `npm run build`/`tsc -b` passed cleanly on
`RunTest.tsx` and `FormControls.tsx` both times a real bug was present — the
console-wipes-on-completion bug and the `Toggle` knob overlap were both invisible to
the type checker and only surfaced by actually driving the running app in a browser
(`claude-in-chrome`) and reading real `getBoundingClientRect()` output for the toggle
specifically, since the overlap wasn't obvious from source review either. Treat a clean
build as necessary, not sufficient, for any frontend change with visual or interactive
stakes.

# Known Constraints

- **One engine run at a time**, by design (see Architectural Decisions). Not a bug.
- **No authentication** anywhere in the stack (API, frontend, Grafana beyond its own
  default admin/admin login) — explicit v1 scope cut per README.
- **Trace/video files are not surfaced via any API** and are not ingested into Postgres —
  only written to disk, and (see next point) not even reliably attributable to a specific
  run once there.
- **`engine/test-results/worker-<n>/` is not namespaced by backend run id** — only by
  Cucumber worker id, with an in-process `scenarioSequence` counter in filenames that has
  no relationship to `TestRun.id`. Only `engine/reports/run-<id>/cucumber.json` is
  reliably run-scoped on disk.
- **No shared-types codegen** between backend DTOs and `frontend/src/types/index.ts` — API
  contract drift is only caught by manual review or runtime `undefined`s, not the type
  checker across the boundary.
- **`CucumberJsonParserService` depends on Cucumber's "legacy" JSON formatter shape** —
  fragile to `@cucumber/cucumber` major version upgrades.
- **50MB max request/multipart size** (`application.yml` — `spring.servlet.multipart`),
  relevant if any future feature uploads files through the backend.
- **Grafana's Postgres datasource uses the same `postgres` superuser** as the app
  (`grafana/provisioning/datasources/postgres.yml` — `PG_USER`/`PG_PASSWORD` default to
  `postgres`/`postgres` in docker-compose), i.e. there's no separate read-only DB role for
  Grafana today, even though it only ever needs read access.

# Future Opportunities

(Derived from the README's own "out of scope for v1" notes plus gaps identified during
this analysis — these are observations for the user to prioritize, not a queued backlog.)

- `GET /api/runs/{id}/artifacts` to list/serve trace `.zip` and video `.webm` files from
  `reportDirectory` — explicitly suggested in the README itself as "a good follow-up."
- Namespace `engine/test-results/worker-<n>/` artifacts by backend `TestRun.id` (not just
  worker id + in-process counter), which is close to a prerequisite for the above being
  reliable.

  single highest-leverage change for enabling any future failure-analysis or self-healing
  agent (see AI / Agent Architecture).
  A `locator_healing_suggestion`-style table + review UI, following the pattern already
  used by `StepsExplorer`/`ScenarioGrid` for evidence display — the most tractable
  self-healing entry point given the existing locator-registry architecture.
- A dedicated read-only Postgres role for Grafana, instead of sharing the app's
  superuser credentials.
- Auth in front of `/api/**` (Spring Security) before any deployment beyond a trusted
  local network — explicit README recommendation, not yet acted on.
- Commit the Gradle wrapper (`gradlew`/`gradlew.bat` + `gradle/wrapper/`) and add
  `eslint` as an actual frontend devDependency — both are documented/scripted as if
  present but aren't (see Known Issues); low effort, closes a real onboarding gap.

  style "pass rate by environment" Grafana panel — `run_environment` is already exposed
